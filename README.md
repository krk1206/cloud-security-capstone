# 졸업작품 통합 개발 계획

## 클라우드 인프라 자율 보안 패치 파이프라인
### Confidence-Gated Cloud Infrastructure Auto-Remediation

> AWS 클라우드 인프라(Terraform)의 설정 오류를 1차 대상으로, 컨테이너 이미지 취약점(Trivy)을 보조 대상으로 자동 탐지하고, AI Agent가 패치의 확신도(confidence)를 스스로 평가해 자율성 수준을 조절하며 패치 코드를 작성·PR까지 자율 생성하는 클라우드 네이티브 DevSecOps 파이프라인

- **사전 학습:** 2026년 9월 2일(화) ~ 9월 7일(일)
- **본 개발:** 2026년 9월 8일(화) ~ 11월 24일(화) — 이 기간 안에 전체 파이프라인이 테스트를 통과하고 완전히 동작하는 것이 목표
- **발표 준비:** 12월 초중순
- **인원:** 3명
- **개발 원칙:** Depth-first, Vertical Slice 우선, 재현성과 평가 가능성 우선
- **최종 완성 기준:** 클라우드 설정 오류 최소 3개 유형(IAM 과다권한, 퍼블릭 S3, 과다 개방 보안그룹) + 컨테이너 CVE 보조 + confidence 3단계(자율/승인필요/미패치) 동작, Rule-based baseline 대비 정량 비교까지 실제로 테스트 완료된 상태

---

## 1. 프로젝트 최종 정의와 핵심 3축

이 프로젝트는 모든 클라우드 보안 문제를 다루지 않는다. Terraform으로 관리되는 AWS 인프라의 설정 오류를 1차 연구 대상으로 삼고, 컨테이너 이미지 취약점은 보조 대상으로 다룬다. AI Agent는 탐지된 문제를 그대로 자동 수정하지 않고, 패치의 위험도(confidence)를 스스로 평가해 자율성 수준을 세 단계로 조절한다.

### 1.1 핵심 3축

| 축 | 역할 | 필수 산출물 |
|---|---|---|
| **클라우드 인프라 (1차)** | Terraform/AWS 설정 오류 탐지 및 패치의 중심 무대 | Trivy(IaC 모드) 연동, CIS AWS Benchmark 매핑, 3개 이상 설정 오류 유형 |
| **컨테이너 취약점 (보조)** | 애플리케이션 레벨 CVE를 함께 다뤄 커버리지 확장 | Trivy(컨테이너 모드) 연동, confidence 프레임워크 동일 적용 |
| **AI Agent (Confidence-Gated)** | 패치를 만들지 말지, 자동으로 낼지 사람에게 넘길지 스스로 판단하는 계층 | confidence scoring 로직, Reasoning·Action, 근거 로그 |

```
Terraform 코드 변경 / 컨테이너 이미지 빌드
  ↓
Trivy(IaC 모드, 1차) + Trivy(컨테이너 모드, 보조) 스캔
  ↓
CIS AWS Benchmark 매핑 + 코드 컨텍스트 수집 (Evidence Bundle)
  ↓
AI Agent: 패치 방향 분석 + confidence 등급 판정
  ├─ High  → 패치 브랜치 생성 → PR 자동 생성 → (경량 승인 후) 병합
  ├─ Medium → 패치 브랜치 생성 → PR 생성 + 회귀 테스트 첨부 → 승인 필수
  └─ Low   → 패치 시도 안 함 → 리포트만 생성 + 미패치 사유 기록
  ↓
병합 후 재스캔(Re-scan) → 설정 오류 제거 + 정상 기능 보존 확인
```

### 1.2 최종 연구 질문

1. AI Agent가 Trivy(IaC 모드)/Trivy(컨테이너 모드)가 탐지한 문제를 CIS AWS Benchmark 등 공인 기준에 맞춰 올바르게 해석하고 패치 방향을 결정하는가?
2. Confidence-Gated(3단계 자율성 조절) 방식이, 전부 자동 또는 전부 수동인 이분법적 방식보다 안전성(부작용·오탐)과 속도(MTTR)를 동시에 개선하는가?
3. Rule-based baseline(고정 규칙 자동 수정)과 비교했을 때, AI Agent가 더 다양한 설정 오류 유형에 일반화된 패치를 생성하는가?

### 1.3 핵심 차별점

1. 컨테이너 취약점이 아닌 **클라우드 인프라(IaC) 설정 오류를 1차 연구 대상**으로 삼는 자율 패치 파이프라인
2. 상용 도구(Dependabot/Snyk Fix 등)처럼 전부 자동 또는 전부 수동인 이분법이 아니라, **AI가 자기 패치의 확신도를 스스로 평가해 자율성 수준을 조절**하는 구조
3. 패치 근거를 **CIS AWS Benchmark 조항에 매핑**해 왜 이렇게 고쳤는지 설명 가능하게 함
4. `terraform plan` 미리보기 + 격리된 샌드박스 AWS 계정에서만 실행하는 안전한 실행 구조
5. Rule-based baseline과의 정량 비교(성공률, MTTR, 부작용률)로 confidence-gating의 효과를 실험적으로 검증

### 1.4 신뢰 경계

| 구성요소 | 신뢰 수준 | 원칙 |
|---|---|---|
| Trivy(IaC 모드) / Trivy(컨테이너 모드) | 관측 데이터 신뢰 | 원본 스캔 결과를 변경 없이 보존 |
| AI Analyzer (LLM) | 불신 판단기 | 패치안과 confidence 등급만 제안, 직접 실행 권한 없음 |
| Confidence Scorer | 신뢰 경계 | 사전 정의된 위험도 기준(변경 리소스 종류, blast radius)으로 등급 산정, AI가 임의로 등급을 올릴 수 없음 |
| Policy Validator | 신뢰 경계 | 패치 diff가 화이트리스트를 벗어나면 등급과 무관하게 거부 |
| Executor (GitHub Actions bot) | 최소 권한 신뢰 | 승인된 PR만 생성, `terraform apply`는 별도 승인 없이 자동 실행 금지 |
| 사람 승인자 | 최종 결정권 | Medium/Low 등급의 최종 승인자, High 등급도 병합 전 최소 확인 필요 |

**명시적 제외 범위**

- 실제 운영 중인 프로덕션 AWS 계정 대상 실험 (격리된 샌드박스 계정만 사용)
- `cluster-admin`/`AdministratorAccess` 등 관리자급 IAM 정책의 완전 자동 재작성
- 사람 확인 없는 `terraform apply` 자동 실행
- High confidence를 포함한 모든 등급에서 완전 무인 자동 병합

## 2. Confidence 등급 설계

| 등급 | 조건 예시 | AI Agent 동작 |
|---|---|---|
| **High** | 포트 범위 축소, 단일 리소스의 명백한 오탈자성 설정, 애플리케이션 CVE의 단순 마이너 버전 업그레이드 | 패치 브랜치 + PR 자동 생성, 경량 승인(1인 확인)만으로 병합 가능 |
| **Medium** | IAM 정책 범위 축소, 보안그룹 규칙 재구성, 메이저 버전 업그레이드 | 패치 브랜치 + PR 생성, `terraform plan` 결과·회귀 테스트 첨부, 승인 필수 |
| **Low** | 패턴화되지 않은 복합 설정, 근거 evidence 부족, 여러 리소스에 걸친 광범위 변경 | 패치 시도하지 않고 `request_review` 리포트만 생성, 미패치 사유를 근거와 함께 기록 |

등급 산정 기준(변경 리소스 종류, 영향받는 리소스 수, 되돌리기 난이도)은 개발 4주차에 사전 고정하고, 이후 결과를 보고 등급 기준을 바꾸지 않는다.

## 3. 시스템 구조

```
┌──────────────────── Dev ────────────────────┐
│ GitHub Actions: Terraform 변경 감지 + 컨테이너 빌드 │
└─────────────────────┬─────────────────────────┘
                       ▼
┌──────────────────── Sec ────────────────────┐
│ Trivy(IaC 모드, 1차, CIS 매핑) + Trivy(컨테이너 모드, 보조) 스캔          │
│ 기준 미달 시 배포 차단, Evidence Bundle 생성      │
└─────────────────────┬─────────────────────────┘
                       ▼
┌───────────────── AI Agent ─────────────────┐
│ Reasoning: 위반 조항·코드 컨텍스트 분석          │
│ Confidence Scorer: High/Medium/Low 판정        │
│ Action: (등급별) 패치 브랜치 → PR 자동 생성       │
└─────────────────────┬─────────────────────────┘
                       ▼
┌──────────────── 승인·검증 ────────────────┐
│ 등급별 승인 절차 → 병합 → terraform apply(수동 확인) │
│ → 재스캔(Re-scan) → 정상 기능 보존 확인          │
└─────────────────────┬─────────────────────────┘
                       ▼
┌──────────────────── Ops ────────────────────┐
│ AWS 샌드박스 계정 / EKS 반영                    │
└───────────────────────────────────────────────┘
```

## 4. 환경 구성

```
GitHub Repository
├─ .github/workflows/       # CI/CD 파이프라인
├─ infra/                   # Terraform (의도적 설정 오류 포함, AWS 샌드박스 대상)
├─ app/                     # 취약한 의존성을 포함한 샘플 애플리케이션 (보조)
├─ ai-agent/                # Reasoning · Confidence Scorer · Action
├─ policy/                  # 패치 화이트리스트, CIS 매핑 테이블
└─ data/sessions/           # 세션별 스캔 리포트, confidence 판정, PR 기록
```

- **AWS 샌드박스 계정**: 실습·평가 전용으로 별도 분리, 프로덕션 자원과 격리
- **Trivy(IaC 모드, `trivy config`)**: IAM, 보안그룹, S3, EKS RBAC 등 CIS AWS Benchmark 매핑 대상 룰 우선 사용. *(tfsec은 2023년 Aqua Security가 개발을 중단하고 Trivy로 룰셋을 통합했으므로, 별도 도구 대신 Trivy의 IaC 스캔 모드를 사용한다. 룰 ID(`AVD-AWS-*`)는 그대로 유지되어 CIS 매핑 작업을 그대로 재사용할 수 있다.)*
- **Trivy(컨테이너 모드, `trivy image`)**: 컨테이너 이미지 OS·라이브러리 취약점 보조 스캔
- **AI Agent 프레임워크**: LangChain/LangGraph 기반 Reasoning-Action 루프

## 6. 사전 학습 기간 (9월 2일 화 ~ 9월 7일 일)

이 기간에는 코드를 짜지 않는다. 9월 8일부터 바로 실습에 들어갈 수 있도록, 3인 모두 기초 개념부터 숙지하는 게 목표다. 첫 이틀은 공통, 이후는 역할별로 나눠서 각자 담당 영역을 예습한다.

### 9/2 (화) — 공통: DevSecOps·Git 기초
- CI/CD 파이프라인의 기본 구조 (빌드-테스트-배포), Shift-Left 보안이 왜 필요한지
- Git 기초 (커밋, 브랜치, PR 개념), GitHub 저장소 구조 익히기

### 9/3 (수) — 공통: 컨테이너·Actions 기초
- Docker/컨테이너 기본 개념 (이미지, 컨테이너, Dockerfile)
- GitHub Actions 워크플로우 문법 (trigger, job, step) — 공식 문서로 간단한 workflow 하나 직접 작성해보기

### 9/4 (목) — 역할별 착수
- **A**: AWS 기초 — IAM, EC2, S3, 보안그룹, VPC 개념. AWS 콘솔/CLI 한 번씩 실습
- **B**: Python 기초 점검, LLM API(OpenAI/Claude API) 호출 방법과 JSON 구조화 출력 개념
- **C**: GitHub Actions 심화 (secrets 관리, PR 이벤트 트리거), REST API 기본 개념

### 9/5 (금) — 역할별 심화 ①
- **A**: Terraform 기초 — HCL 문법, `resource`/`variable`/`provider` 구조, `plan`과 `apply`의 차이. 튜토리얼로 리소스 하나 직접 만들어보기
- **B**: LangChain/LangGraph 개념 — Agent, Tool, Chain, Node/Edge. 공식 튜토리얼 실습
- **C**: GitHub API로 PR 생성·댓글 작성 연습, Trivy 설치 및 기본 사용법

### 9/6 (토) — 역할별 심화 ②
- **A**: CIS AWS Benchmark 개념과 대표 위반 항목(과다 IAM 권한, 퍼블릭 S3, 과다 개방 보안그룹) 조사, Trivy IaC 모드(`trivy config`) 사용법
- **B**: Function Calling/Tool Calling 개념, Prompt Engineering 기초(구조화된 JSON 출력 유도), Reasoning-Action 패턴 이해
- **C**: Trivy 컨테이너 모드(`trivy image`) 사용법, 평가지표 기초 조사(정확도, MTTR이 무엇인지)

### 9/7 (일) — 공통: 통합 리뷰
- 3인 전체 아키텍처 리뷰 회의
- Evidence Bundle 스키마 초안을 함께 논의 (A/B/C 사이의 데이터 인터페이스 합의)
- confidence 등급 개념 공유, 9월 8일 착수 계획 최종 점검

**완료 기준:** 3인 모두 자기 역할에 필요한 도구를 한 번씩 손으로 만져봤고, 전체 파이프라인 흐름을 서로에게 설명할 수 있다.

## 12. 참고: 심화 이론 (사전 학습 기간 이후에도 필요시 참고)

- **IaC와 Terraform**: resource/variable/provider 구조, `plan`과 `apply`의 차이
- **CIS AWS Benchmark**: 클라우드 설정 보안 모범사례가 무엇이고 왜 표준으로 쓰이는가
- **클라우드 IAM 최소 권한 원칙**: 과다 권한이 왜 위험한가
- **AI Agent의 Reasoning-Action 구조**: LLM Function Calling, 판단과 실행을 분리하는 이유
- **AI 입력 보안**: 리소스명·태그 등은 공격자가 조작 가능한 불신 데이터로 취급, 근거 부족 시 `abstain` 허용
- **실험 타당성**: 평가 지표와 반복 횟수를 결과 확인 전에 고정, 개발용/평가용 시나리오 분리

## 17. 최종 완료 정의

1. 클라우드 설정 오류 최소 3개 유형을 반복 가능하게 탐지한다
2. Trivy(IaC 모드)/Trivy(컨테이너 모드) 결과를 CIS 근거와 함께 Evidence Bundle로 구조화한다
3. AI Agent가 confidence 등급을 스스로 판정하고, 등급별로 다른 자율성 수준으로 동작한다
4. 승인 절차를 거쳐 패치가 병합되고, 재스캔으로 효과를 검증한다
5. Rule-based baseline과 confidence-gated AI Agent를 같은 기준으로 비교한다
6. 결과는 성공률뿐 아니라 실패·오탐 사례 분석과 함께 제시한다
7. 11월 24일까지 전체 파이프라인이 실제 테스트를 통과하고 안정적으로 동작한다

더 많은 스캐너를 나열하는 프로젝트가 아니라, 클라우드 인프라의 설정 오류를 AI가 스스로의 확신도에 따라 다르게 대응하고, 그 판단이 실제로 안전하고 효과적인지 정량적으로 증명하는 시스템을 만드는 프로젝트다.
