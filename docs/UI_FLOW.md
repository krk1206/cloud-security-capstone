# 화면 흐름

## 새 프로그램 (첫 화면 `/`, 2026-11-01 — D-31)

사용자는 V1~V8 을 배우려고 프로그램을 여는 게 아니라 "내 인프라에 문제가 있나 · 고쳐도 되나 · 서비스는 그대로인가" 를 알려고 연다. 화면 = 그 질문 순서.

| 단계 | 질문 | 보여 주는 것 | 자료 (서버) |
|---|---|---|---|
| 1 | AI가 수정한 클라우드 인프라, 그대로 적용해도 될까요? | 준비 상태 한 줄 + 예제 카드 4개(팀 3계층 요청 1 SSH · 요청 2 S3 · 요청 3 IAM — 깃허브 main 사본, D-51 → 3계층 — AWS 시험 환경 실측; 게시판 · 2계층은 숨김 — D-47 · D-49) + 내 프로젝트 카드. 요청 카드에 '고객 요청 N · 가상'. 폴더 연결은 버튼을 눌러야 펼침. 설명 글 · 안내 카드 없음 | `/api/p/projects` (`proposal` 표시, `?all=1` 이면 숨긴 예제도) |
| 2 | 내 인프라가 지금 어떻게 구성되어 있지? | **기본 = 흐름 그림** (D-48): 상자 = 출발지(인터넷 · IP 대역) · 보안 그룹이 붙은 묶음, 화살표 = 보안 그룹 허용(포트, 위험한 허용은 빨강), 상자 숫자 = 보안 문제 수. VPC · 서브넷 · 게이트웨이 · IAM · S3 는 그리지 않음. [전체 보기] 단추는 13차에 뺐다 (D-49) — 코드의 리소스 전부(AWS 구성도, D-33)는 서버 모델에 그대로 있고 IAM 요구사항 묶음의 ⑤ ⑥ 그림에만 쓴다: VPC · 공개/비공개 서브넷(코드의 라우팅 기준) · 게이트웨이 · 로드밸런서 → 서비스 · DB · 캐시 · VPC 밖 서비스(IAM 역할 → 정책 대상, S3 · 로그), 선 = 요청 경로 · 보안 그룹 허용 · 권한. 그림만 (리소스 목록 · 읽는 법 카드는 11차, 숫자 네 칸은 17차에 뺌 — 리소스 · 허용 · 위험 수는 왼쪽 메뉴 ② 밑). **IAM 요청(요청 3)은 권한 그림** (D-51): 상자 = 역할 · 리소스, 선 = 권한(동작 · 리소스 짝, 넓은 권한 빨강). **정책 밖 요청(요청 2)은 맨 위 '사람에게 넘김' 칸** | `/api/p/infra` (`web/archmap.py`, `verify/sg_scan.py`) |
| 3 | 우리 회사가 원하는 구조는 이거다 | **왼쪽 = 설계도만 그린 그림, 오른쪽 = 통신 목록** (D-34). 설계도가 없으면 **자동 기준 v1**(지금 코드 − 위험한 통신, D-33). 팀 3계층 예제는 v1 = **팀 설계 문서(DESIGN.md)의 허용 통신을 옮긴 초안** + 왼쪽 아래 '팀 설계 문서' 원문 칸 (D-49, 고객 제안서 예제와 같은 방식). 고객 제안서 예제는 v1 = **제안서를 옮긴 초안** + 왼쪽 아래 '고객 제안서' 원문 칸 — 담당자가 맞춰 보고 확정 (D-46). 목록 한 줄 = 출발 → 도착 : 포트 [허용]/[막기], 인터넷 · IP 대역 출처는 '이 IP만 허용', VPC 대역 출처는 '이 서버만 허용', '통신 추가' → 바로 미리보기(저장 안 함) → 저장 = 새 버전. '지금 코드와 다른 곳 N개' = ④ 의 설계 위반. 그림 = 흐름 그림 (D-48 · D-49: [전체 보기] 없음). IAM 요청(요청 3)은 'IAM 요구사항 v1' = 팀 설계 문서에서 옮긴 초안 — [요구사항 v1] · [지금 코드와 비교] 단추 권한 그림 + 확정 (D-51). 요청 2 는 '해당 없음 (사람에게 넘김)' | `/api/p/design` (`compare.view` · `compare.rows`), `/api/p/structure/preview` · `save` (`web/structure.py`, `web/archmap.design_view`) |
| 4 | 어떤 보안 문제가 있지? | **고칠 수 있는 문제**(⑤ 로 이어짐)를 먼저, 탐지만 되는 나머지는 한 줄로 접음(고칠 것이 없으면 펼침), 그림은 목록 아래 (11차). Trivy 전체(한국어 제목 + 원문) + 자체 보안 그룹 검사 + 설계 위반 + IAM 요구사항, 같은 문제는 한 줄. 누르면 무엇 · 왜 · 어떻게 · 코드 위치 · 근거 + 그림에서 그 자리 강조 (상자를 누르면 그 상자의 문제로). 흐름 그림에 없는 리소스(IAM · S3 등)는 '통신 그림에는 없는 리소스 (목록만)'. 규칙을 따로 쓴 코드(aws_vpc_security_group_ingress_rule)도 그 규칙의 선을 강조하고, Trivy · 자체 검사 · 설계 비교가 같은 문제를 찾으면 한 줄 (D-49) | `/api/p/issues`, 검사 범위 표 `/api/p/coverage` |
| 5 | 어떤 수정 방법이 더 안전하지? | 수정안 = **큰 버튼 1~4**(manifest featured, D-47 — 프로젝트를 열 때 · 설계도 확정 뒤 배경에서 **미리 분석**해 두어 누르면 바로 오른쪽 그림) · AI 수정은 시도마다 · **설계도대로 자동 수정**(규칙 기반 · AI 아님 — D-45) · 직접 제출. **그림 하나** (D-48): 번호를 누르면 그 그림이 '수정안 N 적용 후 — 이렇게 됩니다' 로 바뀜 — 설계도대로 파랑, 설계도와 다름 빨강(✕ · 막힘 점선) + '설계도와 다른 곳' 목록, [고객 설계도 vN] 단추로 같은 자리에서 설계도 (고르기 전에는 설계도). 순서 = 수정안 번호 → 그림 → 결과(바꾼 통신 · 해결 · 새 문제 · AI 시도 기록) → 다른 방법(AI · 설계도대로 자동 수정 · 내 파일). IAM 요청은 권한 그림 [적용 후] · [IAM 요구사항] 단추 — 요구사항 밖 권한 빨강 · 꼭 필요한데 없어진 권한 빨간 점선 + '이 수정안이 바꾼 권한' (D-51) | `/api/p/impact` (`design_view` · `arch_after` · `overlay_after`), `/api/review`, `/api/llm/fix`, `/api/llm/runs` |
| 6 | 이 수정 코드를 적용해도 될까? | 결론 + 질문 5개(기존 문제 해결? 새 문제? 코드가 올바른가? 관련 없는 변경? 고객 구조 유지? — IAM 요청은 '고객이 허용한 권한만 남았나요?', D-51) — V 번호는 자세히에만. 그림은 ⑤ 에서 (17차: ⑥ 아래 같은 그림은 뺌). 지킨 고객 조건의 근거는 접힘([근거 보기]) | `/api/p/verdict` |
| 7 | AWS 시험 환경에 반영하면 제대로 작동할까? | **5단계를 이 화면 안에서 끝까지 (9차, D-43)**: 원본 반영 → 수정 전 측정 → 수정안 반영 → 수정 후 측정 → 시험 환경 삭제. 5칸 띠(지금 · 끝 · 차단 · 안 함) + '다음 할 일' 칸(상황마다 버튼 하나, `flow2.stage2Plan` 의 key 로 문장 선택). 반영 · 삭제 = plan 계산 → 확인 창 '실행 전 확인 (아직 반영 안 됨)' 에서 사람이 체크 + [apply 실행]/[destroy 실행] (닫으면 '취소 — 반영하지 않음'). 측정 = 읽기만, 화면에서 반영이 성공한 뒤 시간이 되면 자동 1회(끄기 가능). 결과 칸 = 이 기록의 V7 · V8. 시험 환경이 없는 프로젝트는 미검증. 전문가 화면 링크는 원본 증거 보기용 | `/api/p/testbed` (상태 + 측정 요약) · `/api/testbed/use` · `/api/plan_check` · `/api/testbed/prepare` · `/api/testbed/execute` · `/api/measure` |
| 8 | 최종적으로 무엇을 결정해야 하지? | 해결 · 남음 · 새 문제 · 설계 위반 · 실제 AWS (검증 못 한 것은 맨 아래 끝맺음 '남은 것' — 17차에 위의 결론 칸 · 세 단계 띠 · '검증하지 못한 부분' 칸은 뺌, 결정 칸 제목 옆 '대상: 수정안 이름'). 승인 · 수정 요청 · 재생성 · 폐기. 승인하면 PR 준비 확인(읽기만: git 상태 · 기준 브랜치의 원본 = 검사한 원본) → 미리보기 → 사람이 확인 문구 입력 → PR 만들기 | `/api/p/final`, `/api/decision`, `/api/p/pr_check`, `/api/p/pr` |

화면이 하지 않는 것: 사람 확인 없는 terraform apply · destroy(⑦ 의 반영 · 삭제는 확인 창에서 사람이 체크하고 눌러야 실행, D-19), 병합(merge), 운영 환경 반영. PR 만들기는 사람이 확인 문구를 입력했을 때만.

### 머리말 '할 일' · '다음 할 일' 칸 (2026-11-02 9차 — D-43)

머리말의 **할 일** 한 줄은 고정 문장이 아니라 지금 상태에서 할 일 하나다 (`m_core.registerTodo` — 화면마다 상태 함수). ③ ⑤ ⑦ ⑧ 은 몸통 맨 위에 같은 모양의 **다음 할 일** 칸(`guideCard`: 제목 · 한 문장 · 버튼 1~3개)을 둔다. **17차 (D-53)**: 칸은 할 것이 있을 때만 — ③ 은 확정 뒤 · 팀 작성 평가 기준([다음 ▶] 하나뿐)이면 빼고, ⑤ 는 설계도가 초안이라 승인을 막는 경고일 때만 둔다(나머지는 머리말 '할 일' 과 같은 말 · 아래에 같은 단추). 아래 표의 문장은 머리말 '할 일' 에 그대로 쓰인다.

| 화면 | 상황 → 다음 할 일 |
|---|---|
| ③ | 설계도 없음 → ② 로 / 바꾸는 중 → [저장 → v(n+1)] / 3계층 예제(팀 작성 평가 기준) → '바꿀 것 없음' [다음 ▶ 보안 문제] / 고객 제안서 예제 → '제안서에서 옮긴 v1 초안 — 제안서와 맞는지 확인하고 확정' (D-46) / 확정됨 → [다음 ▶] / 초안 → 목록 확인 → [이 설계도 확정하기] (확정 없이 넘어가면 승인 불가) |
| ⑤ | 미리 분석 중 → 'n/4 — 끝난 번호부터' / 설계도 초안 → ③ 확정하면 미리 분석 / 실행 중 → 기다림 / 수정안 통과 → [다음 ▶ 적용 판단] / 확정 전 기준 → ③ 확정 후 [다시 검사] / 막힘 → 이유 + [AI 다시] · [설계도대로 자동 수정] · [팀 수정안] · [내 파일] / AI 결과만 있음(수정안 없음) → 설계도대로 자동 수정 · 내 파일 · 팀 수정안 / 아무것도 없음 → AI 되면 [AI 에게 고치게 하기] + [설계도대로 자동 수정], 안 되면 [설계도대로 자동 수정](기본) · 팀 · 내 파일. 규칙 기반이 수정안을 못 만들면 '수정안 없음' 칩 + ⑥ 결론 '규칙 기반으로는 이 문제를 고칠 수 없습니다' + 이유 (D-45) |
| ⑦ | 위 표 |
| ⑧ | 5칸 띠(결정 고르기 → 이유 · 이름 → 결정 기록 → PR 준비 확인 · 미리보기 → PR 만들기). 승인 불가면 이유 + 나머지 셋 / 결정 고름 → 이유 · 이름 / [결정 기록하기] / 승인 기록 뒤 PR 준비 확인 자동(읽기만) → 막힌 항목 + 할 일 / 통과 → [② 미리보기] / 미리보기 뒤 → [③ PR 만들기] (확인 문구) / PR 만들어짐 → GitHub / 승인 아님 → PR 안 만듦 |

시작 화면에 '가장 짧은 길' 한 줄 (예제 → ④ 고치기 → ⑤ → ⑥ → ⑧ 승인 → PR).

### 설계도 초안 ↔ 확정 · AI 결과 상태 · 판정의 버전 (2026-11-02 8차 — D-36 · D-37 · D-38)

### 내 Terraform 폴더 연결 (2026-11-01 — D-32)

예제(3계층 · 2계층)만이 아니라 아무 Terraform 폴더로 같은 8단계를 돈다.

| 단계 | 연결한 프로젝트에서 달라지는 것 |
|---|---|
| 1 | '새 프로젝트 — 내 Terraform 폴더 연결': 이름 · 전체 경로 → 확인(.tf 목록 · 하위 폴더 .tf · tfstate 유무 · git 저장소) → 연결하고 점검. 폴더는 복사 · 수정하지 않음. 카드의 '연결 끊기'(확인 문구) = 점검 결과 · 고칠 대상만 지움 |
| 2 | 점검 = 실행 전 안전 점검 → 작업 폴더 사본에서 오프라인 plan → Trivy (`POST /api/p/project/create`, `/api/case/scan`) → 원하는 구조가 없으면 자동 기준 v1 저장 (D-33). AWS 를 조회하는 data 소스가 있으면 plan 을 돌리지 않고 '그리지 못함 + 이유' |
| 3 | 자동 기준 v1 에서 시작 — 목록에서 바꾼 것만 v2 로 (`/api/p/structure/save`) |
| 4 | 문제를 고르고 '이 문제 고치기' → 고칠 대상 세트를 그때 만듦 (`POST /api/p/target`). 고칠 대상은 보안 그룹 문제만 (IAM 은 필요한 권한 기준이 없어 탐지만). Trivy 지적이 아닌 문제는 같은 프로젝트의 고칠 수 있는 Trivy 지적과 함께 검사. 원본 plan 이 없으면 고치기 없음(탐지만) |
| 5 | 준비된 실험 후보가 없으므로 AI 수정 칸이 먼저 펼쳐짐. 머리에 '고른 문제 · 함께 고칠 Trivy 지적 · 지켜야 할 설계도' |
| 6 · 7 | 시험 환경이 없으면 결론 = '승인 판단 가능 · 실제 AWS 미검증', ⑦ = 미검증 |
| 8 | 승인 = '실제 AWS 에서 확인하지 않은 것을 알고 승인' 표시 필요(서버도 같은 조건). PR 준비 확인 · 미리보기 · 확인 문구 → 그 폴더가 들어 있는 git 저장소에 새 브랜치, 제목 앞 '[실제 AWS 미검증]' |

## 작업 화면 (`/work`, 2026-10-19 개편 — 전문가용 원본 증거 · 시험 환경)

실행: 저장소 루트의 `IaCPatch.exe` 더블클릭 (또는 `python -m iacpatch.app`). 브라우저가 아니라 프로그램 자체 창(pywebview·WebView2)이 열리고, 창을 닫으면 프로그램이 끝난다. pywebview 가 없으면 Edge 앱 창(주소창 없음)으로 연다.

화면은 사용자의 작업 순서를 따른다. 주차·내부 기능 이름은 화면에 없다. 코드 상태 이름(REVIEW_REQUIRED 등), 파일 경로, 실행 명령, 실행 로그는 기본 화면에 없고 펼침(상세)이나 설정 화면에서만 보인다.

| 단계 | 화면 | 보여 주는 것 | 데이터 |
|---|---|---|---|
| 1 | 요구사항 | 사례 그림, 요구사항 문장(사람이 적은 intent), Trivy 가 찾은 것 중 요구사항이 있는 것만 검토 대상 | `experiments/candidate-sets/<set>/intents/*.json`, `experiments/arch-webapp-2tier/trivy-scan.json` |
| 2 | 현재 설정 | 원본 plan 에 요구사항을 대입한 결과 — 어떤 요구사항을 어기는지, 영향 대상, 근거 규칙 | 원본 plan 캐시(`data/cache/baseline`) 또는 기록의 `local_verify/plan_baseline.json` → `verify/v6` 의 같은 오라클 |
| 3 | 수정 후보 | 후보 목록(출처: 규칙 기반 / 시험용 / 붙여넣기), 후보별 최신 기록의 분류(정상 / 과도한 허용 남음 / 필요한 기능 막음 / 판단 불가 / 차단) | manifest + `data/reviews` |
| 4 | 배포 전 검증 | 결론 한 줄 + 이유 + 다음 할 일, 요구사항별 수정 전/후, 무엇이 바뀌나, 위험도. 8단계 표·허용 범위 검사·실행 정보는 펼침 | 기록 `state/verification/risk/policy.json` |
| 5 | 사람의 판단 | 승인자 확인 목록, 승인(통과한 후보만) / 수정 요청 / 후보 재생성 / 폐기, 승인 시 PR 초안. 승인이 아니면 배포되지 않고 지금 설정이 그대로 남는다 (화면에 표시) | `decision.json` (신규), `tools/github.prepare_pr(execute=False)` |
| 6 | 적용 후 확인 | 적용 후 확인 통과 / 실패 / 미확인 / 적용 대상 아님. 배포 전 차단이 원칙이고, 이 단계는 같은 기준으로 실제 설정(V7)·통신(V8)을 다시 잰다. 측정 명령은 펼침 | 기록 `state.json` 의 `post_deploy`·`recovery` (측정은 CLI 로 사람이) |

새 모듈: `src/iacpatch/web/cases.py`(사례·요구사항·현재 설정), `explain.py`(판정 → 문장·표시명), `decision.py`(사람의 결정 기록). 검증 엔진(`review/`, `verify/`, `policy/`)은 바꾸지 않았다.

(2026-10-19 당시) 화면이 하지 않는 것: LLM API 호출, AWS 접속, git push, PR 생성, terraform apply. 승인은 PR 초안 생성까지였다 — 지금은 새 프로그램 8단계에서 사람이 확인 후 PR 을 만든다 (D-31). 승인이 검증 실패를 덮지 못한다 (버튼 비활성 + 서버 거부).

결과 요약(상단 '결과 요약'): 모든 후보의 가장 최근 검토 결과를 한 표로 — 검증 1~6 단계별 통과/실패/판단 불가, 최종 결과, 사람의 결정, 출처별(규칙 기반·시험용·AI) 통과·차단 수, 후보 1개 자동 검증 평균 시간.
