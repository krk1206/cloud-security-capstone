## 1. 기존 AWS 보안 솔루션과의 차별점

**당시 답변:** 규칙 기반 도구와의 차이를 설명했다.

**정리된 답변:**
탐지 자동화는 이미 업계 표준이다. Trivy, Checkov, tfsec(현재 Trivy에 통합), KICS, Terrascan 같은 IaC 정적 스캐너가 CI에서 설정 오류를 탐지한다. AWS 자체에도 AWS Config 규칙, Security Hub, IAM Access Analyzer 같은 탐지·분석 기능이 있다.
본 프로젝트가 자동화하는 부분은 탐지가 아니라 그 다음 단계다. AI가 만든 수정이 스캐너 통과 여부와 무관하게 실제로 보안 상태를 개선했는지 검증하고(Intent Oracle, 배포 후 실측), 위험도에 따라 자동화 수준을 다르게 적용한다. 선행 연구(TerraProbe)에 따르면 기존 접근은 지목된 경고 제거에서 평가를 멈추며, 사람이 판정한 사례 중 최대 71.4%가 스캐너만 통과한 겉보기 수정이었다.

**후속 조치:**
기존 도구 조사표를 작성한다. 열: 탐지 / 수정 제안 / 수정 검증 / 배포 후 확인 / 위험도 게이팅. 대상: Trivy, Checkov, tfsec, KICS, Terrascan, Snyk IaC, OPA/conftest, Sentinel, AWS Config, Security Hub, IAM Access Analyzer. "기존 도구가 없다"는 주장은 이 표로 확인한 뒤에만 한다. 담당: A. 시점: 3~4주차.

## 2. 비용 및 자원의 최적화

**당시 답변:** 테스트 후 destroy 한다고 답했다.

**정리된 답변:**
AWS 무료 플랜 범위에서 운영한다. 상시 과금 자원(NAT Gateway, EKS, 상시 EC2)은 사용하지 않는다. Budgets 알림(1달러)과 루트 MFA, 작업용 IAM 사용자 분리를 1주차에 완료했다. 모든 자원에 `Project=capstone-2026` 태그를 default_tags로 부여하며, 실험 후 `terraform destroy`를 원칙으로 한다.

**후속 조치:**
- Cost Explorer로 실제 발생 비용을 주 1회 확인하고 작업 기록에 남긴다. 미착수.
- 태그 기준으로 남아 있는 자원을 조회하는 스크립트를 만들고 주기 실행한다(대여받은 라즈베리파이 활용 검토). 미착수.

## 4. 위험도의 기준 정립

**당시 답변:** 추후 정하겠다고 답했다.

**정리된 답변:**
위험도는 AI의 확신도가 아니라 변경 자체의 성격으로 정한다. 기준표(Risk Rubric) 항목: 변경되는 리소스 종류, 변경 리소스 수, IAM 관련 여부, 영향 범위(blast radius), 롤백 난이도. 항목별 점수를 합산해 High / Medium / Low 상한을 정하고, AI가 제시하는 확신도는 등급을 낮추는 방향으로만 반영한다. 기준표는 4주차에 고정하고 실험 결과를 보고 바꾸지 않는다.

**후속 조치:** 4주차에 기준표 확정(담당 B, 팀 합의). 확정 전까지는 "정해지지 않았다"고 답한다. 예정.

## 6. AI의 권한과 사람의 역할

**당시 답변:** AI에게 판정 권한이 없으며 배포 후 실제 상태(V7)로 확인한다고 답했다.

**정리된 답변:**
AI는 패치 후보를 생성하는 한 단계만 담당한다. AI 프로세스에는 AWS 자격증명이 없고, 통과 여부는 결정론적 검증 계층(V1~V6)이 정하며, 배포 전에 반드시 사람이 PR을 승인한다. 배포 후에는 실제 AWS 설정(V7)과 정상 기능(V8)을 다시 확인한다. 검증 계층 중 하나라도 실패하면 등급과 무관하게 PR을 만들지 않는다.

**후속 조치:** 없음. 이 원칙은 README 신뢰 경계 절에 유지한다. 완료.

## 9. "파이프라인"이라는 표현이 맞는가

**당시 상황:** "코드가 올라오면 AI가 수정본을 만들고 8계층으로 검증한 뒤 배포한다"고 설명했고, 그 설명에 자동 실행·실패 시 차단·반복이 드러나지 않아 질문을 받았다.

**정리된 답변:**
파이프라인이라고 부르는 이유는 사람이 단계를 손으로 실행하지 않기 때문이다. Terraform 코드가 PR로 올라오는 것이 트리거이고, 탐지 → 근거 묶음 생성 → AI 패치 후보 생성 → 검증 계층 → 위험도 판정 → PR 생성까지 GitHub Actions가 정해진 순서로 자동 실행한다. 각 단계는 앞 단계를 통과해야 넘어가고, 하나라도 실패하면 거기서 멈추고 결과를 기록한다. 사람이 개입하는 지점은 PR 승인 한 곳이며, 승인 뒤 배포와 사후 검증도 다시 자동이다.
"모든 과정이 자동"이라고 말하지 않는다. 무인 apply는 설계상 금지이며, 사람 승인이 필수라는 점과 충돌하기 때문이다.

**후속 조치:** 발표 자료와 설명 문구를 위 내용으로 정정했다. 완료.
