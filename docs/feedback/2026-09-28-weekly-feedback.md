## 1. Trivy 심각도 게이트

교수 이해: 의도적 결함이 있는 Terraform을 Trivy로 스캔하고, Trivy가 판정한 등급이 높으면 실패 처리해 실제 코드에 반영되지 않게 한다.
구현 (2026-09-28, 커밋 4ff5798):
- `.github/workflows/iac-scan.yml`에 게이트 스텝 추가. PR 이벤트에서만 `trivy config --severity HIGH,CRITICAL --exit-code 1`로 실패 처리. main push는 기록(JSON 아티팩트, 14일 보관)만 남긴다.
- 데모 PR(`demo/gate-check`)로 확인: AWS-0104(CRITICAL), AWS-0107(HIGH) 탐지 → 게이트 스텝 실패 → 체크 실패. 확인 후 PR은 병합하지 않고 닫음.
- 브랜치 보호 규칙(main, 상태 체크 필수)은 GitHub 설정에서 적용. 관리자 우회는 5주차 패치 흐름이 생길 때까지 허용.
설계 결정: 게이트를 PR에만 거는 이유는 현재 `infrastructure/sg-baseline`이 의도적 결함 코드라 main 자체가 HIGH/CRITICAL이기 때문이다. "의도적 결함 시나리오(scenarios/)"와 "배포용 인프라(infrastructure/)"의 폴더 분리는 5주차 패치 흐름과 함께 한다. 그때까지 게이트는 PR에서 변경된 인프라 폴더만 검사한다(팀원의 코드 PR이 기존 결함 때문에 막히지 않도록).
용어: Trivy가 판정하는 등급은 룰에 정해진 심각도(severity)이며, 대상은 취약점(CVE)이 아니라 설정 오류(Misconfiguration)다.
재현성 과제: CI가 설치하는 Trivy와 룰 번들 버전이 실험 시점과 같도록 고정한다(실험 경로 구축 시, 8주차).

## 2. AI 에이전트 실험 자동화와 하네스 제약

대응: 계획서의 실험 경로(샌드박스 전용 자동 apply, 검증 실패 시 자동 revert)와 같은 방향이다. 제약사항은 부록 B에 초안을 두고 4주차에 확정한다. 대여받은 미니PC를 셀프호스트 러너 겸 에이전트 격리 실행 환경으로 쓰는 방안을 검토한다(에이전트 전용 계정, AWS 자격증명 없음, 수정 가능 경로 제한). 라즈베리파이는 비용·잔여 자원 감시와 V8의 승인된 출발지 역할로 검토한다.

## 3. 보안 패치 구현 방식

패치는 Terraform 코드 변경이다.
- 입력: Evidence Bundle. Trivy 경고의 룰 ID·리소스·파일 위치, 해당 코드 블록, 사람이 관리하는 정책 파일의 허용값(승인 CIDR 등)
- 출력: 수정된 .tf 파일과 수정 근거 JSON
- 생성기 두 종을 같은 입력으로 실행한다. 규칙 기반은 템플릿 치환(예: 0.0.0.0/0 → 정책 파일의 승인 CIDR). AI는 Claude Code를 비대화형으로 호출해 같은 형식으로 출력하게 한다.
- 원칙: AI는 값을 지어내지 못한다. 승인 CIDR이나 필요 권한 목록은 정책 파일에서만 오고, 정책 파일에 없는 경우 패치를 만들지 않고 Low 등급 리포트만 낸다.
- 허용되는 변경 범위는 `policy/patch-whitelist.md`(v0.2)에 정의한다. 범위 밖 변경은 등급과 무관하게 차단한다.
- 생성된 패치는 브랜치에 올라가 V1~V6를 통과해야 PR이 된다.
- IAM은 필요 권한을 정책 파일로 정의해야 하므로 난이도가 높다. 초기 실효 판정은 선행 연구 부록 B의 방식(plan JSON에서 정책 문서의 `Resource`/`Action`에 `*`가 남아 있는지 세기)으로 시작하고, 7주차에 재평가한다. 어려우면 "IAM은 무조건 사람 승인"으로 대체한다(계획서에 명시).

## 4. AI 활용 방향 조정

대응: 부록 C의 원칙을 팀 규칙으로 채택한다(팀 합의 필요). 요지: AI가 초안을 쓸 수는 있으나, 담당자가 모든 줄을 설명할 수 있어야 하고, 연습 과제로 직접 수정하며, 작업 기록에 AI 초안 여부를 표기한다.

## 5. 요구사항 기반 Terraform 작성 수준

대응: 학습 과제를 V8 테스트베드와 겹치게 한다. 퍼블릭/프라이빗 서브넷, 인터넷 게이트웨이, 라우팅 테이블, 승인 CIDR만 허용하는 Security Group, 그 뒤의 EC2 인스턴스. 이 환경은 V8(허용 트래픽 통과, 금지 트래픽 차단 확인)에 그대로 필요하다. 팀원 각자 요구사항 문서를 보고 한 번씩 apply와 destroy를 수행한다. 이 Terraform은 AI 초안 없이 직접 작성한다.

## 6. 범위의 한계, 자동화 필요성, 표준 가이드

- 범위 인정: Terraform으로 만들 수 있는 문제는 소프트웨어 취약점이 아니라 설정 오류다. 따라서 대상을 접근 허용 범위(Security Group)와 권한 범위(IAM)로 잡았다.
- 표준: CIS AWS Foundations Benchmark가 항목 단위 기준이다. SK쉴더스 클라우드 보안 가이드(AWS 편)에도 같은 항목의 체크리스트가 있다. 탐지 기준은 이를 따른다. 확인 필요: 교수가 언급한 "SK쉴더스 테라폼 보안 가이드"라는 이름의 문서는 확인하지 못했다. 확인된 것은 SK쉴더스 클라우드 보안 가이드(2021, AWS/Azure/GCP)와 2024 클라우드 보안 가이드북이며, 기사 기준으로 Terraform 항목은 언급되지 않는다. 정확한 문서명을 확인한다.
- 자동화가 필요한 이유는 탐지가 아니라 수정 검증이다. 탐지 자동화는 이미 업계 표준이다. 본 프로젝트가 자동화하는 것은 AI가 만든 수정이 진짜 고쳐졌는지 판정하는 부분이다. 사람이 diff를 봐서는 0.0.0.0/1과 128.0.0.0/1의 합이 전체 인터넷인지 바로 알기 어렵기 때문에 계산으로 판정해야 한다.

## 8. V2 계층 구현 (완료, 초안)

용어 정정: 피드백 메모에 "실효성 검증(V2 계층)"으로 적혀 있으나, V2는 실효성 검증이 아니다. V2는 패치 전후 전체 재스캔을 비교해 새 경고가 늘었는지 확인하는 회귀 확인 계층이다. 실효성 검증은 V6(Intent Oracle, 6주차)이다. 다음 보고에서 이 구분을 명확히 말한다.
구현 (커밋 53e655b): `src/verify/v2_finding_diff.py`. Trivy JSON 두 개에서 `Status == FAIL`인 (룰 ID, 리소스) 집합을 만들어 차집합을 구한다. 새 finding이 있으면 FAIL(종료 코드 1), 없으면 PASS(0), 입력 오류는 2. 줄 번호는 정체 키에서 제외한다(패치로 줄이 밀리기 때문).
확인: `experiments/trivy-sg-probe/results-verify/`의 00-baseline과 01-cidr-split 등 5개 조합으로 기대값 확인. 01-cidr-split(기만 패치)은 V2를 통과한다 — 이것이 정상이며 V6가 필요한 이유다.
작성 방식: AI 초안, 담당자(A)가 설명·수정 책임. 연습 과제 3건(정체 키에 파일명 추가 실험, V1 미리보기 인자 추가, 깨진 JSON 처리)은 미완.

## 9. 8계층의 근거

대응: 부록 A. 핵심 문장은 다음과 같다.
"V1~V5는 TerraProbe 논문의 5계층 오라클을 그대로 가져왔다. V6는 논문이 사람의 판정으로 하던 부분을 자동화한 것이며, 논문 부록 B의 IAM 와일드카드 잔존 탐지기를 Security Group의 실효 허용 대역 계산으로 확장한 것이다. V7·V8은 논문이 배포를 수행하지 않아 하지 못한 것을 샌드박스로 채운 것이다. 논문 부록 E의 CI 파이프라인 체크리스트 4개 게이트는 모두 포함되어 있다. 계층마다 잡는 실패 유형이 하나씩 다르고 겹치지 않으므로 8개다."
팀원 각자 계층별로 (1) 한 문장 정의 (2) 논문의 해당 절 (3) 우리 실험 케이스 번호를 말할 수 있어야 한다. 논문 3.5절(오라클 스택), 3.11절(위협 모델: 위협 4가지, 방어책 3가지), 부록 B(와일드카드 탐지기), 부록 E(CI 체크리스트)는 직접 읽는다. 합쳐서 세 쪽이다.

| V8 정상 기능 확인 | 서비스가 여전히 동작하는가 | 자동 프로그램 수정의 오라클 문제(논문 2.2절, Monperrus): 테스트 통과가 명세 만족을 뜻하지 않음 | 보안은 개선됐으나 서비스 불능(규칙 전체 삭제 등) | 평가 지표 "정상 기능 보존율" |
| 등급 판정·사람 승인 | 누가 최종 결정하는가 | 3.11절 방어책 3, 부록 E 게이트 4 "고권한 리소스 변경은 자동 오라클 통과와 무관하게 사람 검토" | - | Risk Rubric: IAM 관련·경고 증가 시 등급 하향 |

순서 논리: 논문 표현대로 약한 증거에서 강한 증거 순이며, 비용이 싼 검사를 먼저 돌려 비싼 검사(배포)를 아낀다. V1~V6는 배포 전, V7~V8은 배포 후.
왜 5개가 아니라 8개인가: 논문 5계층만으로는 논문 스스로 판정 사례의 71.4%가 통과한다고 보고했다. 논문이 제안한 방어책 3가지가 각각 V5, V6, 등급 판정이 되었고, 배포 후 확인 2개는 샌드박스가 있어 추가할 수 있었다.
논문 부록 B와의 차이: 부록 B 탐지기는 plan JSON에서 `*` 문자열이 남았는지 세는 방식이라 IAM 와일드카드에는 유효하지만, CIDR을 쪼개는 우회(01 케이스)에는 `*`가 없어 잡지 못한다. V6는 문자열이 아니라 허용 대역의 합집합을 계산한다.
왜 더 넣지 않는가: 런타임 공격 시뮬레이션 등은 IaC 검증 범위 밖이다.

## 부록 B. 에이전트 하네스 제약사항 (초안)

1. 호출: 비대화형 실행만 허용. 프롬프트와 입력 파일을 고정하고, 출력은 파일(패치, 근거 JSON)로만 받는다.
2. 권한: 에이전트 프로세스에 AWS 자격증명을 두지 않는다. apply는 파이프라인 단계가 샌드박스에서만 실행한다.
3. 파일 범위: 해당 시나리오 폴더의 .tf만 수정 가능. 그 외 경로가 변경되면 즉시 실패. 세부 범위는 `policy/patch-whitelist.md`를 따른다.
4. 명령 범위: fmt, validate, plan만 허용. apply, destroy, AWS CLI 금지.
5. 재시도: validate 또는 plan 실패 시 최대 2회. 초과 시 Low 등급.
6. 기록: 프롬프트 버전, 모델 출력 해시, 실행 시각을 보존한다(논문 3.6절 Provenance Ledger 방식).
7. 실험 경로: V6 또는 V7 실패 시 자동 revert. 태그 기반 자원 정리. 예산 알림.
8. 평가 격리: 개발용 시나리오와 평가용 시나리오를 분리하고, 지표를 사전에 고정한다.

## 부록 C. AI 활용 원칙 (팀 합의 필요)

배경: 팀원이 아직 직접 작성하기 어려운 모듈이 있어 "AI 초안 금지"는 현실적이지 않다. 대신 다음을 지킨다.

- AI가 초안을 작성할 수 있다. 단, 담당자는 (1) 모든 줄을 자기 말로 설명할 수 있어야 하고 (2) 연습 과제로 직접 수정한 커밋을 남기며 (3) 작업 기록과 커밋 메시지에 "AI 초안"임을 표기한다.
- AI 초안 없이 직접 작성하는 것: V8 테스트베드 Terraform, Risk Rubric 표(판단이므로), 실험 결과 해석, 지도교수 대상 설명 문서.
- AI에 맡기지 않는 것: 실험 결과의 해석과 결론, 근거 문서의 최종 문장.
- 예외: Claude Code 패치 생성기. 이는 실험 대상이므로 AI가 수행한다.
- 증명: 커밋은 본인 계정으로, 주간 회의에서 본인 코드를 설명하며, 설명하지 못하는 코드는 병합하지 않는다.

핵심 모듈 담당:

| 모듈 | 담당 | 내용 | 작성 방식 |
|---|---|---|---|
| V2 전후 비교 | A | Trivy JSON 두 개에서 (룰 ID, 리소스) 집합 차이 | AI 초안 완료, 연습 과제 미완 |
| V6 Intent Oracle | B | plan JSON에서 SG 규칙 수집, `ipaddress`로 합집합 계산, 0.0.0.0/0이 덮이면 실패 | 미착수 |
| V5 plan 차이 검사 | C | plan JSON의 변경 리소스·속성이 화이트리스트 안인지 | 미착수 |
| 규칙 기반 baseline | C | 0.0.0.0/0을 정책 파일의 승인 CIDR로 치환 | 미착수 |
| Risk Rubric | 전원 합의 | 어떤 변경이 High/Medium/Low인지 | 직접 작성 |
| 시나리오 .tf, V8 테스트베드 | 각자 / A | 손으로 작성 | 직접 작성 |
