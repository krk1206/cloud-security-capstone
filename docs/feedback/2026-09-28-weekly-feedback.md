## 1. Trivy 심각도 게이트

교수 이해: 의도적 결함이 있는 Terraform을 Trivy로 스캔하고, Trivy가 판정한 등급이 높으면 실패 처리해 실제 코드에 반영되지 않게 한다.
대응: 계획서 2주차 항목과 동일하다. 현재 워크플로우는 스캔 결과를 아티팩트로 저장하는 단계까지 확인했고, 실패 처리는 아직 없다.
조치:
- `trivy config --severity HIGH,CRITICAL --exit-code 1` 로 HIGH 이상이면 워크플로우 실패
- 브랜치 보호 규칙에서 iac-scan 체크 통과를 병합 조건으로 설정
- 확인 화면: PR의 실패 체크와 병합 버튼 비활성
용어: Trivy가 판정하는 등급은 룰에 정해진 심각도(severity)이며, 대상은 취약점(CVE)이 아니라 설정 오류(Misconfiguration)다.

## 2. AI 에이전트 실험 자동화와 하네스 제약

대응: 계획서의 실험 경로(샌드박스 전용 자동 apply, 검증 실패 시 자동 revert)와 같은 방향이다. 제약사항은 부록 B에 초안을 두고 3~4주차에 확정한다. 대여받은 미니PC를 셀프호스트 러너 겸 에이전트 격리 실행 환경으로 쓰는 방안을 검토한다(에이전트 전용 계정, AWS 자격증명 없음, 수정 가능 경로 제한).

## 3. 보안 패치 구현 방식

패치는 Terraform 코드 변경이다.
- 입력: Evidence Bundle. Trivy 경고의 룰 ID·리소스·파일 위치, 해당 코드 블록, 사람이 관리하는 정책 파일의 허용값(승인 CIDR 등)
- 출력: 수정된 .tf 파일과 수정 근거 JSON
- 생성기 두 종을 같은 입력으로 실행한다. 규칙 기반은 템플릿 치환(예: 0.0.0.0/0 → 정책 파일의 승인 CIDR). AI는 Claude Code를 비대화형으로 호출해 같은 형식으로 출력하게 한다.
- 원칙: AI는 값을 지어내지 못한다. 승인 CIDR이나 필요 권한 목록은 정책 파일에서만 오고, 정책 파일에 없는 경우 패치를 만들지 않고 Low 등급 리포트만 낸다.
- 생성된 패치는 브랜치에 올라가 V1~V6를 통과해야 PR이 된다.
- IAM은 필요 권한을 정책 파일로 정의해야 하므로 난이도가 높다. 7주차에 재평가하고, 어려우면 "IAM은 무조건 사람 승인"으로 대체한다(계획서에 명시).

## 4. AI 활용 방향 조정

대응: 부록 C의 원칙을 팀 규칙으로 채택한다(팀 합의 필요). 핵심 모듈은 손으로 작성하고, AI는 리뷰·오류 설명·문서 교정에 쓰며, 도움받은 부분은 작업 기록에 표기한다.

## 5. 요구사항 기반 Terraform 작성 수준

대응: 학습 과제를 V8 테스트베드와 겹치게 한다. 퍼블릭/프라이빗 서브넷, 인터넷 게이트웨이, 라우팅 테이블, 승인 CIDR만 허용하는 Security Group, 그 뒤의 EC2 인스턴스. 이 환경은 V8(허용 트래픽 통과, 금지 트래픽 차단 확인)에 그대로 필요하다. 팀원 각자 요구사항 문서를 보고 한 번씩 apply와 destroy를 수행한다.

## 6. 범위의 한계, 자동화 필요성, 표준 가이드

- 범위 인정: Terraform으로 만들 수 있는 문제는 소프트웨어 취약점이 아니라 설정 오류다. 따라서 대상을 접근 허용 범위(Security Group)와 권한 범위(IAM)로 잡았다.
- 표준: CIS AWS Foundations Benchmark가 항목 단위 기준이다. SK쉴더스 클라우드 보안 가이드(AWS 편)에도 같은 항목의 체크리스트가 있다. 탐지 기준은 이를 따른다. 확인 필요: 교수가 언급한 "SK쉴더스 테라폼 보안 가이드"라는 이름의 문서는 확인하지 못했다. 확인된 것은 SK쉴더스 클라우드 보안 가이드(2021, AWS/Azure/GCP)와 2024 클라우드 보안 가이드북이며, 기사 기준으로 Terraform 항목은 언급되지 않는다. 정확한 문서명을 확인한다.
- 자동화가 필요한 이유는 탐지가 아니라 수정 검증이다. 탐지 자동화는 이미 업계 표준이다. 본 프로젝트가 자동화하는 것은 AI가 만든 수정이 진짜 고쳐졌는지 판정하는 부분이다. 사람이 diff를 봐서는 0.0.0.0/1과 128.0.0.0/1의 합이 전체 인터넷인지 바로 알기 어렵기 때문에 계산으로 판정해야 한다.

## 7. Trivy와 CIS AWS Benchmark 매핑표

조치:
- trivy-checks 저장소의 룰 메타데이터(frameworks 항목)에서 CIS 대응 정보를 확인한다.
- 벤치마크 버전을 명시한다. 후보 항목: Security Group 관리 포트 개방(IPv4, IPv6), IAM 전체 권한 정책 금지. 항목 번호는 버전별로 다르므로 원문 확인 후 기입한다.
- 표 열: Trivy 룰 ID / 룰 설명 / CIS 항목 번호·제목 / 대응 수준(직접, 부분, 없음) / 우리 시나리오. 대응이 없는 룰도 그대로 적는다.

## 8. V2 계층 구현

용어 정정: 피드백 메모에 "실효성 검증(V2 계층)"으로 적혀 있으나, V2는 실효성 검증이 아니다. V2는 패치 전후 전체 재스캔을 비교해 새 경고가 늘었는지 확인하는 회귀 확인 계층이다. 실효성 검증은 V6(Intent Oracle, 6주차)이다. 다음 보고에서 이 구분을 명확히 말한다.
조치: V2 구현(Trivy JSON 두 개에서 (룰 ID, 리소스) 집합 차이 계산). 담당 A, 3주차.

## 9. 8계층의 근거

대응: 부록 A. 핵심 문장은 다음과 같다.
"V1~V5는 TerraProbe 논문의 5계층 오라클을 그대로 가져왔다. V6는 논문이 사람의 판정으로 하던 부분을 자동화한 것이다. V7·V8은 논문이 배포를 수행하지 않아 하지 못한 것을 샌드박스로 채운 것이다. 계층마다 잡는 실패 유형이 하나씩 다르고 겹치지 않으므로 8개다."
팀원 각자 계층별로 (1) 한 문장 정의 (2) 논문의 해당 절 (3) 우리 실험 케이스 번호를 말할 수 있어야 한다. 논문 3.5절(오라클 스택)과 위협 모델 절(위협 4가지, 방어책 3가지)은 직접 읽는다.

## 부록 A. 검증 8계층 근거표

선행 연구: TerraProbe (arXiv:2606.26590, 2026-06). 논문 수치는 Gemini-2.5-flash-lite, n=96 기준이며 "연구에 따르면"으로 인용한다.

| 계층 | 답하는 질문 | 출처 | 잡는 실패 유형 | 근거 |
|---|---|---|---|---|
| V1 지목 경고 제거 | 지목된 경고가 사라졌는가 | 논문 3.5절 Layer 1 (Targeted Finding Removal) | 아무것도 고치지 않음 | 논문 L1 통과 83.3% |
| V2 전체 재스캔 | 다른 경고가 새로 생겼는가 | 논문 Layer 2 (Full Scanner Rerun), 위협 유형 "new-finding introduction" | 하나를 고치고 다른 것을 망가뜨림 | 논문 L2 통과 10.4% |
| V3 fmt/validate | 문법과 스키마가 유효한가 | 논문 Layer 3 (Structural Validation) | 코드 자체가 깨짐 | 논문 L3 통과 90.6% |
| V4 plan | 배포 계획이 생성되는가 | 논문 Layer 4 (Planning) | 참조·타입 오류로 배포 불가 | 논문 L4 통과 39.6% |
| V5 plan JSON 차이 | 변경이 허용 범위 안인가 | 논문 Layer 5 (Plan Comparison), 방어책 1 "plan 산출물로 승인 게이트" | 허용 범위 밖 변경, scope manipulation | 논문 L5 통과 38.5% |
| V6 Intent Oracle | 실제 허용 범위가 줄었는가 (스캐너 무관) | 논문 방어책 2 "수정 전후 실효 권한 비교"의 Security Group 판, 논문 3.8절 사람 판정의 자동화 | syntactic bypass, 즉 기만적 패치 | 우리 실험 01·06 케이스(9종 중 2종 Trivy 우회), 논문 판정 사례 중 71.4% |
| V7 배포 후 실측 | 실제 AWS 상태가 계획과 같은가 | 논문의 한계: "No terraform apply step is run", "plan JSON is the strongest evidence available before deployment" | plan과 실제 상태 불일치, prefix list 전개 후 노출 | 우리 06 케이스는 전개해야 드러남 |
| V8 정상 기능 확인 | 서비스가 여전히 동작하는가 | 자동 프로그램 수정의 오라클 문제(논문 2.2절, Monperrus): 테스트 통과가 명세 만족을 뜻하지 않음 | 보안은 개선됐으나 서비스 불능(규칙 전체 삭제 등) | 평가 지표 "정상 기능 보존율" |
| 등급 판정·사람 승인 | 누가 최종 결정하는가 | 논문 방어책 3 "고권한 리소스 변경·경고 증가 시 사람 검토 필수" | - | Risk Rubric: IAM 관련·경고 증가 시 등급 하향 |

순서 논리: 논문 표현대로 약한 증거에서 강한 증거 순이며, 비용이 싼 검사를 먼저 돌려 비싼 검사(배포)를 아낀다. V1~V6는 배포 전, V7~V8은 배포 후.
왜 5개가 아니라 8개인가: 논문 5계층만으로는 논문 스스로 판정 사례의 71.4%가 통과한다고 보고했다. 논문이 제안한 방어책 3가지가 각각 V5, V6, 등급 판정이 되었고, 배포 후 확인 2개는 샌드박스가 있어 추가할 수 있었다.
왜 더 넣지 않는가: 런타임 공격 시뮬레이션 등은 IaC 검증 범위 밖이다.

## 부록 B. 에이전트 하네스 제약사항 (초안)

1. 호출: 비대화형 실행만 허용. 프롬프트와 입력 파일을 고정하고, 출력은 파일(패치, 근거 JSON)로만 받는다.
2. 권한: 에이전트 프로세스에 AWS 자격증명을 두지 않는다. apply는 파이프라인 단계가 샌드박스에서만 실행한다.
3. 파일 범위: 해당 시나리오 폴더의 .tf만 수정 가능. 그 외 경로가 변경되면 즉시 실패.
4. 명령 범위: fmt, validate, plan만 허용. apply, destroy, AWS CLI 금지.
5. 재시도: validate 또는 plan 실패 시 최대 2회. 초과 시 Low 등급.
6. 기록: 프롬프트 버전, 모델 출력 해시, 실행 시각을 보존한다(논문 3.6절의 재현성 기록 방식).
7. 실험 경로: V6 또는 V7 실패 시 자동 revert. 태그 기반 자원 정리. 예산 알림.
8. 평가 격리: 개발용 시나리오와 평가용 시나리오를 분리하고, 지표를 사전에 고정한다.

## 부록 C. AI 활용 원칙 (팀 합의 필요)

- 허용: 개념 질문, 에러 메시지 해석, 본인이 작성한 코드에 대한 리뷰, 문서 교정
- 금지: 핵심 모듈(V2, V5, V6, Risk Rubric, 규칙 기반 baseline, 시나리오 Terraform) 초안 생성, 실험 결과 해석 대행, 근거 문서 초안 생성
- 예외: Claude Code 패치 생성기. 이는 실험 대상이므로 AI가 수행한다.
- 증명: 커밋은 본인 계정으로, 주간 회의에서 본인 코드를 설명하며, 작업 기록에 AI 도움을 받은 부분을 표기한다.
