# 독립 평가 절차 — 누가 · 무엇으로 · 어떻게 세나 (2026-11-02, D-42)

검토 문서(11-02) 2번 6 · 7항: "독립 평가 설계 — 대조군, 개발에 쓰지 않은 평가 세트, 외부 평가자 입력, 오탐 · 미탐 · 검증 불가 · 환경 오류를 **따로** 세기."
이 문서는 절차만 정한다. 결과 수치는 실행한 뒤 `experiments/**/results-history/` 에 사람이 넣는다 (CLAUDE.md: 실측 기록은 사람이 바꾼다). **실험 결과를 보고 기준을 바꾸지 않는다** — 이 문서의 판정 기준과 집계 표는 실행 전에 고정한다.

## 1. 평가 대상과 대조군

| 축 | 평가 대상 | 대조군 | 같은 입력 · 같은 검사 |
|---|---|---|---|
| 수정안 생성 | AI 수정 (llmfix, Claude Code 구독 · 도구 없음 · 최대 3번) | **규칙 기반 생성기**(`rule-based` 수정안, LLM 아님) · 사람이 고친 파일(직접 제출) | 세 가지 모두 같은 8개 관문 · 같은 정책 · 같은 설계도 버전으로 검사한다 (기록의 '이 판정의 버전' 이 같아야 비교) |
| 검증기 | 8개 관문 (V1~V6 배포 전, V7 · V8 시험 환경) | Trivy 단독 (V1 · V2 만) · 사람 검토자(아래 §4) | 같은 수정안 묶음 |

## 2. 평가 세트 — 개발용과 평가용 분리

| 묶음 | 용도 | 기대 결과 고정 시점 | 비고 |
|---|---|---|---|
| `experiments/candidate-sets/arch-3tier-sg` (25개) · `arch-webapp-sg` · `arch-webapp-iam` | **개발 · 회귀** — 코드를 고칠 때 이걸 보고 고쳤다 | 2026-10-20 · 10-02 (실행 전, manifest `expected`) | 이 묶음의 통과율은 '개발 중 맞춘 값' 이라 성능 주장에 쓰지 않는다 |
| `eval-seeded-sg` · `eval-a-probe-rule` (A 의 probe 7개) | 개발 중 작성한 평가용 — 코드에 맞춘 적 없음을 보장하지 못함 | 2026-09-15 · 09-22 | 참고 자료 |
| **held-out 묶음** (새로 만든다) | **최종 평가** — 프로그램 개발자가 아닌 사람(A · C 또는 외부)이 작성, 기대 결과도 그 사람이 적음, 개발자는 실행 전까지 보지 않음 | 작성 즉시 sha256 을 `results-history/` 에 적고 봉인 | 최소 10개: 보안 그룹 8 (분할 대역 · IPv6 · 포트 범위 · 여러 SG · 참조 · 필수 통신 제거 · 정책 범위 밖 · 정상) + IAM 2 |

held-out 묶음은 **한 번만** 돌린다. 돌린 뒤 코드를 고쳤으면 '고친 뒤 다시 돌림' 이라고 표에 적고 첫 결과도 지우지 않는다.

## 3. 집계 표 — 네 가지를 섞지 않는다

수정안 하나 = 한 줄. 판정은 기록(`data/reviews/<id>/`)에서 옮겨 적는다.

| 수정안 | 기대 결과 (작성자) | 프로그램 결론 | 맞음? | 오탐 FP | 미탐 FN | 검증 불가 | 환경 오류 | 시도 수 | 비고 |
|---|---|---|---|---|---|---|---|---|---|

정의 (실행 전 고정):
- **맞음**: 기대 결과와 프로그램 결론(통과 · 설계 위반 · 차단 · 판정 불가)이 같다.
- **오탐(FP)**: 기대는 '통과' 인데 프로그램이 막았다 (설계 위반 · 차단 · 새 문제).
- **미탐(FN)**: 기대는 '막혀야 함' 인데 프로그램이 통과시켰다. **가장 위험한 칸** — 하나라도 있으면 원인(어느 계층이 놓쳤나)을 적는다.
- **검증 불가**: 프로그램이 UNKNOWN(판정 불가)으로 끝냈다. 기대가 '판정 불가' 면 맞음으로 세고, 아니면 FP 도 FN 도 아닌 **별도 칸**으로 센다 (사람 검토로 넘어간 것 — 자동 승인은 없었으므로 안전 쪽).
- **환경 오류**: 도구 · provider · 입력 문제로 검사가 돌지 않음(TOOL_ERROR · 계층 ERROR). 프로그램 판정 성능과 **섞지 않는다** — 환경을 고치고 다시 돌린 결과를 따로 적는다.
- 집계: 맞음률 = 맞음 / (전체 − 환경 오류). FP 율 · FN 율은 각 분모(기대 통과 수 · 기대 차단 수)로. "정확도" 라는 말을 쓸 때는 이 중 무엇인지 적는다.

AI 수정 실행(llmfix)은 따로: 실행 하나 = 한 줄 — 상태(PASSED · GAVE_UP · REPEATED · AI_ERROR · TOOL_ERROR · UNDECIDABLE) · 시도 수 · 걸린 시간 · 마지막 시도의 계층 결과. 통과율 = PASSED / (전체 − AI_ERROR − TOOL_ERROR).

## 4. 외부 평가자 입력 (사람 검토 대조)

1. 평가자(프로그램 개발자 아님) 2명 이상에게 held-out 수정안의 **코드 차이(diff)와 설계도**만 준다 — 프로그램 결과는 주지 않는다.
2. 평가자는 수정안마다 통과 · 설계 위반 · 차단 · 모르겠음 중 하나와 이유를 적는다 (제한 시간 기록).
3. 그 뒤 프로그램 결과를 보여 주고, 다른 곳마다 **누가 맞았나**를 기대 결과(작성자)로 가린다.
4. 표: 평가자 판정 vs 프로그램 판정 vs 기대 결과 — 사람이 놓친 것(프로그램이 잡음) · 프로그램이 놓친 것(사람이 잡음) · 둘 다 놓친 것을 따로 센다. 이것이 docs/OUT_OF_SCOPE.md 의 가설 H1 자료다.
