## 1. 논문 분석과 그 영향

### 무엇을 읽었나

TerraProbe는 LLM이 생성한 Terraform 보안 패치를 5단계 오라클로 평가한 연구다.

| 오라클 | 내용 |
|---|---|
| L1 | 지목된 스캐너 finding이 제거됐는가 |
| L2 | 전체 스캔이 깨끗한가 |
| L3 | `terraform validate` 통과 |
| L4 | `terraform plan` 성공 |
| L5 | plan JSON을 패치 전후로 비교 |

핵심 수치.

- L1 통과 **83.3%**, L2 통과 **10.4%** — 여덟 배 격차
- 실제 GitHub 코드에서 plan 비교까지 간 패치의 **57.1~71.4%가 기만적 패치**
- 모델 3종(Gemini·GPT-4o·Claude) 간 유의한 차이 없음 → 구조적 문제

### 프로젝트에 미친 영향

기존 계획은 "재스캔에서 오류가 사라지면 성공"이었다. 그것이 논문에서 말하는 **L1 하나뿐**이고,
**구조적으로 부적절한 성공 기준**이라는 것이 확인됐다.

이 때문에 검증을 8계층으로 확장하고, 그중 V6(Intent Oracle)를 신설하기로 했다.

## 2. Trivy 우회 실험

### 왜 했나

논문은 **Checkov** 기준이다. 우리는 **Trivy**를 쓴다. 논문 8.1절도
"스캐너가 다르면 기만 패턴도 다를 수 있다"고 명시했다. 그러므로 직접 측정해야 했다.

### 케이스 9종

    00-baseline      cidr_blocks = ["0.0.0.0/0"]              ← 대조군
    01-cidr-split    ["0.0.0.0/1", "128.0.0.0/1"]             ← 합집합이 전체
    02-var-default   variable 기본값 경유
    03-string-build  join() 으로 문자열 조합
    04-dynamic       dynamic 블록으로 생성
    05-separate      별도 aws_vpc_security_group_ingress_rule
    06-prefix-list   managed prefix list 참조
    07-ipv6-only     IPv4는 닫고 ipv6_cidr_blocks = ["::/0"]
    08-second-sg     대상 SG는 조이고 인접 SG는 개방

### 결과

|---|---|---|---|
| 00-baseline | 70 | 1 | FAIL |
| **01-cidr-split** | **71** | **0** | **PASS** |
| 02-var-default | 70 | 1 | FAIL |

**01과 06이 우회했다.**

## 3. 결과를 의심한 과정 — 오늘 가장 중요한 부분

### 왜 의심했나

9개 스캔이 **1분 만에** 끝났다. "너무 빠른데 제대로 돈 게 맞나?"

이 의심이 결과적으로 옳았다. 검증 없이 넘어갔으면 "Trivy가 못 잡더라" 수준의
주장밖에 못 했을 것이고, 교수에게 "파일이 깨진 거 아니냐"는 질문을 받았을 때 답이 없었다.

> **실제로 1분은 정상이었다.** `trivy config`는 네트워크를 쓰지 않고 파일만 파싱하므로
> 빠른 게 맞다. 느린 것은 `trivy image`(레이어 풀고 패키지 DB 대조) 쪽이다.
> 그러나 **정상이라는 것을 확인한 것**과 **막연히 넘어간 것**은 다르다.

### 검증 A — 룰이 실제로 실행됐는가

"0 FAIL"에는 두 가지가 있다.

    ① 룰을 돌렸는데 통과       ← 진짜 우회
    ② 파일을 아예 안 읽음      ← 실험 오류

구분하는 방법.

    trivy config <dir> --include-non-failures --format json

`--include-non-failures`를 붙이면 **PASS 기록까지** 나온다.
01과 06에서 `AWS-0107`이 `Status=PASS`로 찍혔다. 즉 **그 룰이 이 파일을 검사했고
명시적으로 통과시켰다.** 스캔 실패 가능성이 배제됐다.

보조 근거로 `MisconfSummary.Successes` + `Failures` 합계가 전 케이스에서 71로 동일했다.
같은 룰셋이 같은 개수로 돌았다는 뜻이다.

### 검증 B — 최소 쌍 대조

01을 통째로 복사한 뒤 **CIDR 한 곳만** 바꿔 01b를 만들었다.

    변경 전 (01)    cidr_blocks = ["0.0.0.0/1", "128.0.0.0/1"]   → 0 FAIL
    변경 후 (01b)   cidr_blocks = ["0.0.0.0/0"]                  → 1 FAIL

파일 구조·리소스명·문법이 동일하고 CIDR 값만 다르다.
→ **판정을 가른 원인이 CIDR임이 확정.**

`make_control.py`가 diff를 출력하게 만들어서, 정말 한 줄만 바뀌었다는 것을
눈으로 확인할 수 있게 했다. **그 diff 자체가 증거물이다.**

### 검증 C — 문법 유효성

    terraform init -backend=false
    terraform validate

깨진 HCL을 Trivy가 조용히 넘어간 것이라면 우회가 아니라 그냥 오류다.
01, 01b, 06 전부 valid였다.

### 판정 기준

세 개를 **모두** 만족해야 우회로 인정하기로 했다.

    A. 통과룰 > 0 또는 0107 = PASS   → 룰이 실행됐다
    B. 01b는 FAIL, 01은 0 FAIL       → 원인이 CIDR이다
    C. terraform validate 통과        → 배포 가능한 코드다

이 원칙을 이후 모든 실험에 적용한다.
**0 FAIL을 우회로 판정하기 전에 반드시 대조군을 둔다.**

## 4. 01-cidr-split 이 왜 중요한가

    0.0.0.0/1     = 0.0.0.0    ~ 127.255.255.255
    128.0.0.0/1   = 128.0.0.0  ~ 255.255.255.255
    ─────────────────────────────────────────────
    합집합        = 0.0.0.0    ~ 255.255.255.255  = 0.0.0.0/0

Python으로 검증한 방법.

    python3 -c "import ipaddress as i; print(list(i.collapse_addresses([i.ip_network('0.0.0.0/1'), i.ip_network('128.0.0.0/1')])))"
    # → [IPv4Network('0.0.0.0/0')]

**보안 상태 변화가 0인데 스캐너만 조용해진 것이다.**
그리고 4분할(`/2` 네 개)로 쪼개도 `collapse_addresses`가 합쳐준다.
즉 **얼마나 잘게 쪼개든 잡을 수 있다.**

### 이 결과가 V6 설계를 결정했다

만약 V6를 이렇게 만들었다면

    if "0.0.0.0/0" in cidr_blocks:   # 잘못된 구현
        return FAIL

**01도 06도 그대로 통과한다.** 01엔 그 문자열이 없고, 06엔 `cidr_blocks` 필드 자체가 없다.

올바른 V6.

    ① 해당 포트로 들어오는 모든 출처 수집
       cidr_blocks + ipv6_cidr_blocks + prefix_list_ids(전개) + 참조 SG
    ② CIDR 합집합 계산 — 문자열 매칭 금지
    ③ 공인 인터넷을 덮으면 FAIL (Trivy 판정과 무관하게)
    ④ 인스턴스/ENI에 붙은 모든 SG를 합산

### CLI 연결

    # 설치 (apt/snap 대신 공식 스크립트 — 버전이 최신)
    curl "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o awscliv2.zip
    unzip -q awscliv2.zip && sudo ./aws/install

    # 프로필 설정
    aws configure --profile capstone

    # 확인
    aws sts get-caller-identity --profile capstone
    # → Arn 이 user/capstone-admin 이어야 한다. root 면 키가 잘못된 것

    # VPC ID 확보 (Terraform 입력값)
    aws ec2 describe-vpcs --filters "Name=isDefault,Values=true" \
      --query "Vpcs[0].VpcId" --output text --profile capstone

### Terraform 파일 구조

`infrastructure/sg-baseline/`

| 파일 | 역할 |
|---|---|
| `provider.tf` | 어느 클라우드에 어떻게 접속할지. 버전 잠금, 공통 태그 |
| `variables.tf` | 입력 변수의 **정의** |
| `terraform.tfvars` | 변수의 **실제 값**. 계정별로 다르므로 커밋 안 함 |
| `main.tf` | 만들 리소스 |
| `outputs.tf` | 만든 뒤 꺼내 쓸 값 |

Terraform은 디렉터리의 모든 `.tf`를 합쳐 읽는다. 한 파일에 다 써도 동작은 같다.
나누는 것은 사람이 보기 위한 관례다.

### 핵심 설계 결정

**버전 잠금**

    required_version = ">= 1.5"
    aws = { version = "~> 5.0" }

`~> 5.0`은 "5.x는 되고 6.0은 안 됨". 프로바이더 메이저 버전이 올라가며 문법이 바뀌면
어제 되던 코드가 오늘 깨진다. Trivy 버전을 기록하는 것과 같은 이유다.

**액세스 키를 코드에 쓰지 않음**

    provider "aws" {
      profile = "capstone"   # 키가 아니라 프로필 이름만
    }

실제 자격 증명은 `~/.aws/credentials`에 있고 저장소 밖이다.
공개 저장소에 키가 올라가면 자동화된 스크립트가 수분 내에 찾아내 악용한다.

**공통 태그**

    default_tags {
      tags = { Project = "capstone-2026", ManagedBy = "terraform", Purpose = "security-research" }
    }

이 프로바이더로 만드는 **모든** 리소스에 자동 부여된다. 나중에 태그로 찾아서 한 번에 지울 수 있다.

**egress를 명시한 이유**

`aws_security_group`에 `egress` 블록을 하나도 쓰지 않으면 Terraform이
기존 아웃바운드 규칙을 **모두 제거한다.** AWS 콘솔 기본 동작(전체 허용)과 달라서
인스턴스를 붙였을 때 외부 통신이 막힌다.

**EC2를 붙이지 않은 이유**

현 단계에 필요한 것(정적 스캔, plan, apply 후 상태 조회)은 SG만으로 전부 가능하다.
EC2는 정상 기능 검증(V8, 9주차)에서 추가한다. 22번이 열린 인스턴스는
공개 인터넷에서 자동화된 접속 시도의 대상이 된다.

### 실행 순서와 각 명령의 의미

    terraform init      # 프로바이더 다운로드 (~840MB). 최초 1회
    terraform fmt       # 들여쓰기 정리
    terraform validate  # 문법·스키마 검사. AWS 접속 안 함
    terraform plan      # 무엇이 바뀔지 예측. 실제 변경 없음
    terraform apply     # 실제 생성. 확인 프롬프트에 yes 를 다 쳐야 함
    terraform destroy   # 삭제

> `y`가 아니라 **`yes`** 를 전부 입력해야 한다. 되돌리기 어려운 명령을
> 실수로 넘기지 않게 하려는 의도적 설계다.

### 배포 후 실측 (V7의 원형)

    aws ec2 describe-security-groups \
      --group-ids $(terraform output -raw sg_id) \
      --query "SecurityGroups[0].IpPermissions" \
      --profile capstone

결과.

    {
      "IpProtocol": "tcp", "FromPort": 22, "ToPort": 22,
      "IpRanges": [{ "CidrIp": "0.0.0.0/0" }],
      "Ipv6Ranges": [],
      "PrefixListIds": []
    }

**Terraform 코드와 실제 AWS 상태가 일치한다는 것을 처음으로 증명했다.**

이 JSON 구조가 V7의 입력이 된다. `IpRanges`만 보면 prefix list 우회(06)를 놓치므로
`Ipv6Ranges`, `PrefixListIds`까지 모두 모아야 한다.

## 7. 막혔던 지점

가장 중요한 절이다. 같은 실수를 반복하지 않기 위해 남긴다.

### .gitignore가 서브폴더에만 있었다

`experiments/trivy-sg-probe/.gitignore`를 만들었는데, **그 폴더에만 적용된다.**
`infrastructure/sg-baseline/terraform.tfvars`가 커밋될 뻔했다.

`git status --short`에서 발견해 막았다.

    git reset HEAD infrastructure/sg-baseline/terraform.tfvars

그 뒤 **루트** `.gitignore`에 Terraform 규칙을 추가했다.

> **교훈: `git add` 후 반드시 `git status --short`로 확인한다.**
> 한 번 커밋되면 파일을 지워도 과거 커밋에서 조회된다.

### GitHub 페이지 캐시

`web_fetch`로 README를 세 번 가져왔는데 **세 번 모두 같은 캐시본**이었다.
그 사이 팀이 수정한 내용이 반영되지 않아, 하마터면 좋아진 부분을 덮어쓸 뻔했다.

> **교훈: 파일 확인은 로컬 `grep`이나 브라우저 기준으로 한다.**

### 다운로드 경로 (Windows vs WSL)

    C:\Users\krk\Downloads          (Windows)
    /mnt/c/Users/krk/Downloads      (WSL에서 보는 같은 폴더)

WSL에서 역슬래시 경로를 쓰면 `C:UserskrkDownloads`로 뭉개진다.

그리고 Windows를 거친 파일은 줄 끝에 `\r`이 붙는다.

    sed -i 's/\r$//' 파일명

### 정규식이 표를 망가뜨렸다

특수문자를 지우면서 이 줄을 함께 실행했다.

    txt = re.sub(r"\|\s+\|", "| |", txt)

`\s`가 **줄바꿈도 포함**하기 때문에 마크다운 표의 행 경계가 전부 붙어버렸다.
9행짜리 표가 한 줄이 됐다.

커밋 전이라 `git checkout -- .`으로 되돌렸다.

> **교훈: 텍스트 일괄 치환 뒤에는 결과 구조를 확인한다.
> `\s`는 줄바꿈을 포함한다.**

### sed 구분자 충돌

    sed -i 's| A | B |' 파일    # 내용에도 | 가 있어서 깨짐

마크다운 표를 `sed`로 고치려다 실패했다. Python으로 처리하는 것이 안전하다.

### 붙여넣기 시 백틱 중첩

문서 안에 코드블록(백틱 3개)이 있으면 터미널 붙여넣기가 중간에 끊긴다.
**4칸 들여쓰기**로 코드를 표기하면 같은 효과에 안전하다.

### GitHub 토큰 workflow 권한

    ! [remote rejected] refusing to allow a Personal Access Token to
      create or update workflow .github/workflows/... without workflow scope

워크플로 파일은 **`repo`와 별개로 `workflow` 권한**이 필요하다.
토큰을 새로 만들며 체크했다.

## 10. 개념 정리

### terraform plan 과 validate 의 차이

| | 검사 대상 | AWS 접속 |
|---|---|---|
| `validate` | 문법, 스키마 | 안 함 |
| `plan` | 실제 상태와 비교해 변경 예정 사항 | **함** |

둘 다 **보안 검사 도구가 아니다.** 보안 검사는 `trivy config`가 한다.

### Security Group ingress / egress

| | 방향 | 기본값 |
|---|---|---|
| ingress | 들어오는 트래픽 | 전부 거부 |
| egress | 나가는 트래픽 | 전부 허용 |

`from_port`/`to_port`가 같으면 단일 포트, 다르면 범위다.
`protocol = "-1"`은 모든 프로토콜을 의미한다.

### Misconfiguration 과 Vulnerability

| 용어 | 뜻 |
|---|---|
| **Misconfiguration** | 정상 기능을 잘못 설정해 생긴 위험 — **이 프로젝트의 대상** |
| Vulnerability (CVE) | 소프트웨어 자체의 결함 |

발표에서 섞어 쓰면 지적을 받는다.

### git pull --rebase 를 쓰는 이유

그냥 `git pull`은 merge 커밋을 하나 만든다. `--rebase`는 내 커밋을
원격 커밋 **위에 얹어** 히스토리가 일직선으로 유지된다.

### .gitignore의 적용 범위

`.gitignore`는 **자기가 있는 디렉터리와 그 하위**에만 적용된다.
저장소 전체에 적용하려면 **루트**에 둬야 한다.
