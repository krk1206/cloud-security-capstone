# 범위 밖 · 부분 구현 표 — 기업에서 쓰려면 더 있어야 하는 것 (2026-11-02, D-41)

검토 문서(11-02)가 기업 요구사항으로 든 항목마다 **지금 상태를 코드 기준으로** 적는다. '있음' 이라고 적은 것은 코드 · 시험 위치가 있고, '없음' 은 발표 · 문서에서 있다고 말하지 않는다.
이 캡스톤의 연구 질문은 "Terraform 변경의 위험도 · 영향 범위를 평가하고 수정안마다 자율성을 다르게 줬을 때 안전성과 처리 효율의 균형" 이다 — 아래 항목은 그 질문의 바깥이거나, 1인 PC 프로그램(exe) 이라는 전제에서 뺀 것이다.

| 기업 요구사항 | 지금 상태 | 어디에 · 어떻게 | 왜 범위 밖 · 하려면 |
|---|---|---|---|
| AI 에게 보내는 자료 통제 (어떤 데이터가 외부로 나가나) | **부분** | 보내는 것은 Trivy 지적 한 건 + 대상 .tf 파일 전체 + (선택) 설계도 JSON 뿐 (`llmfix.build_prompt`). 요청문 전문과 sha256 을 기록하고 ⑤ 에서 'AI 에게 보낸 요청' 으로 볼 수 있다. 보내지 않는 것: tfvars · state · AWS 자격증명(프로세스 환경에서 제거 `UNSET_ENV`) · 기대 결과 | 파일 안에 비밀이 적혀 있으면 그대로 나간다 — **비밀 탐지 · 가리기 없음**. 하려면 요청문 생성 전에 비밀 패턴(키 · 토큰 · 암호 값) 검사 · 차단 단계 |
| 비밀 가리기 (로그 · 기록 · PR) | **없음** (규칙만) | AI 작업 규칙(CLAUDE.md)이 .env · tfstate · tfvars 를 읽지 않게 하고, 직접 제출에서 .tfvars 는 '지원 안 함' 으로 거른다 (`web/submission.py`). Actions 사본은 계정 번호를 로그 · 아티팩트에서 가린다 (`docs/actions/terraform-plan.yml`) | 프로그램이 기록(data/reviews) · PR 본문에 쓰는 값은 plan · 코드에서 온 것이라 비밀이 섞일 수 있다. 하려면 기록 저장 전 마스킹 단계 + 비밀 스캐너(gitleaks 등) 연동 |
| 읽기 권한과 변경 권한의 분리 | **없음** (프로그램 안에) | 배포 전 검사(V1~V6)는 AWS 권한이 필요 없다. 시험 환경 반영 · 삭제(apply · destroy)는 사람이 확인 창에서만 누르고(`/api/testbed/execute`, D-19), AI 와 자동 단계는 AWS 를 바꾸는 명령을 부르지 않는다 (`test_exec_guard`) | 1인 PC 프로그램이라 사용자 계정 · 역할 개념이 없다. 권한 분리는 OS 사용자와 AWS IAM(읽기 전용 역할 ↔ 변경 역할)에서 한다. 하려면 로그인 · 역할(검토자 · 승인자 · 운영자)과 서버 측 권한 검사 |
| 팀 승인자 · 다중 승인 | **부분** | 결정 기록에 결정한 사람 이름 · 이유를 남기고(`web/decision.py`), 설계도 · 요구사항 확정에도 이름이 필수(D-38 · D-40). 승인 조건(배포 전 통과 · 설계도 확정 · 시험 환경 결과 또는 미검증 확인)은 서버가 다시 검사한다 | 이름은 자유 입력(인증 없음), 승인자 한 명. 하려면 인증 + 승인자 목록 + 2인 승인 규칙 — GitHub 쪽은 브랜치 보호 규칙(필수 리뷰어)으로 대신할 수 있다 |
| 예외 처리 (허용 예외 · 만료일) | **없음** | 설계도에 통신을 추가하는 것이 '예외' 에 가장 가깝지만 만료일 · 승인자 · 사유 필드가 없다 (버전 메모만) | 하려면 설계도 통신마다 `expires` · `approved_by` 와 만료 뒤 자동 위반 처리 |
| 복구 절차 | **있음 (사람 실행)** | `postdeploy.py` 복구: 원본 파일 복원 → plan → apply(사람 승인) → plan 재실행으로 변경 없음 확인 + describe 실측 → 그때만 RECOVERED (`RECOVERY_INCOMPLETE` 구분). git 되돌리기만으로 '복구됨' 이라 하지 않는다 | 시험 환경(3계층)에서만 돌려 봄. 운영 환경 절차(점검 창 · 알림 · 담당자)는 문서화 대상 |
| 맹목적 자동 롤백 금지 | **있음** | 자동 롤백 코드가 없다. 실패는 상태(DEPLOY_FAILED · PLAN_BLOCKED · UNVERIFIED)로 남기고 사람에게 넘긴다 | — |
| 운영 환경 반영 | **하지 않음 (설계)** | 프로그램은 PR 까지. 병합 · apply 는 사람. ⑥⑦⑧ 세 단계 띠에 '운영 반영 — 확인 안 함' 을 항상 적는다 (D-39) | 연구 질문 밖. 운영 반영 뒤 검증(V7 · V8 을 운영에서)은 하려면 운영 계정 읽기 권한과 변경 창 합의가 필요 |
| GitHub Actions 에서 실제 흐름 (사용자 코드 + 설계도 입력) | **부분** | 사본 `docs/actions/iacpatch-ai-fix.yml` 은 저장소 안의 실험 세트(set 입력)에 대해 같은 llmfix 를 돌리고 결과 상태로 성공 · 실패를 정한다(D-36). iac-scan · terraform-plan 사본은 보고 · 게이트 대상 · 판 고정을 고쳤다(D-41) | 아무 폴더 + 설계도를 입력으로 받는 Actions 는 없다(프로그램의 '내 폴더 연결' 은 PC 전용). **실제 러너 실행 기록은 아직 없다** — `.github/` 는 사람이 올리고, 첫 실행 로그를 `docs/CI_FIRST_RUN.md` 에 적는다 |
| 사용자 인증 · 다중 사용자 웹 서비스 | **없음** | 로컬 PC 에서 127.0.0.1 로만 여는 프로그램 (exe) | 범위 밖. 하려면 서버 배포 · 인증 · 프로젝트별 권한 |
| 기록의 위변조 방지 | **부분** | 기록마다 입력 · 수정안 · 설계도 사본의 sha256, 프로그램 판 · 커밋 · 소스 지문(D-37)을 적는다. 실패 · 오탐 기록을 지우지 않는다 | 서명 · 외부 보관(WORM) 없음. 하려면 기록을 git 저장소나 서명된 아티팩트로 내보내기 |
| 비용 · 시간 상한 (AI 호출) | **부분** | 시도 횟수 상한(기본 3) · 한 번 호출 시간 제한 · 같은 수정안 반복 중단(D-36). 구독 토큰만 쓰고 API 키(종량 과금)는 환경에서 제거 | 월 상한 · 조직 단위 집계 없음 |
| 대상 리소스 확장 (S3 · RDS · EKS 등) | **없음 (탐지만)** | ④ 는 Trivy 지적을 모두 보여 주지만 수정 · 검증은 보안 그룹과 IAM(Tier 1)만 (`web/product.coverage`, docs/VERIFICATION_SCOPE.md) | 깊이 우선(Depth-first) 원칙. 유형마다 오라클(요구사항 형식 + 판정기)이 있어야 하고, 없는 유형은 '탐지만' 으로 표시한다 |

## 기업 가치 가설 — 잴 수 있는 형태로 (검토 문서 "측정 가능한 가치 가설")

| 가설 | 지표 (프로그램이 이미 기록하는 값) | 지금 있는 자료 | 없는 자료 |
|---|---|---|---|
| H1. 같은 수정안을 사람이 PR 리뷰로만 볼 때보다, 8개 관문 결과표가 붙으면 **검토자가 놓치는 위험(설계 위반 · 분할 대역)이 줄어든다** | 수정안별 V6 위반 수 · ④ 'Trivy 는 못 봄' 수 · 검토자 판정과 오라클 판정의 불일치 수 | 수정안 25개 실측 결과표(`experiments/candidate-sets/arch-3tier-sg/RESULTS_*`), 검증기 변이 시험 | 사람 검토자 집단 실험(독립 평가 절차 — docs/EVAL_PROTOCOL.md 예정) |
| H2. 위험도 · 확신도로 자율성을 나누면 **사람 승인 대기 시간을 뺀 처리 시간**이 줄고 정책 위반 자동 반영은 0 건이다 | 기록의 단계별 시각(started_at · finished_at · 결정 시각), 정책 위반(V5 BLOCKED) 수, 자동 반영 수(항상 0) | 기록 시각은 있음 (`data/reviews/*/state.json`) | 비교 기준선(규칙 기반 · 사람만) 시간의 반복 측정 |
| H3. AI 수정안은 **같은 검사를 통과한 비율**에서 규칙 기반보다 높지 않을 수 있다 — 단순 보안 그룹은 규칙 기반이 더 안정적일 수 있다 | AI 실행의 상태 분포(PASSED · GAVE_UP · UNDECIDABLE…), 시도 수, 규칙 기반 수정안 통과율 | AI 실행 기록(`data/llm_runs`), 규칙 기반 수정안(`rule-based` id) 결과 | 같은 문제 N회 반복 실행 통계 (비용 · 시간 때문에 미실시) |

이 가설들은 "AI 가 항상 낫다" 를 전제하지 않는다. 결과가 반대로 나와도 기록한다.
